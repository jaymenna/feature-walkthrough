# SupplyLane — fictional pitch demo brief

**Status: illustrative example, not a real approval record.** SupplyLane, its organization, users and request data are invented. No customer endorsement or measured result is implied. This example includes a downstream storyboard to illustrate the format; a real engagement must first obtain story agreement or explicit delegation from its user.

## Pitch goals

- **Primary audience:** a procurement coordinator who repeatedly returns incomplete purchase requests.
- **Secondary customer:** an employee who needs to submit a complete request and understand what happens next.
- **Problem:** missing details create repeated clarification messages before a request can even be reviewed.
- **Desired belief:** a guided request and one shared readiness view could reduce avoidable clarification while keeping approval decisions explicit.
- **Proof to show:** a requester sees a missing delivery date, fixes it and submits; the coordinator receives the same complete request with review still pending.
- **Next step:** agree one request type to test using sample data. This is proposed text, not a booking button or a claim that a pilot service exists.
- **Format:** a proposed two-minute concept demo, web workflow first. Actual duration must be measured after narration and visual holds.
- **Audio plan:** narration and captions in the first produced demo. Select a suitable available voice with a short sample from the agreed script before generating the full track. Record actual provider/voice/settings and listening results then; none are selected or auditioned in this planning example. If listening is unavailable, label that review pending and provide playable audio without claiming audible quality was verified.
- **Claim limits:** all product behavior is planned. No implemented backend, supplier integration, automated approval, cost savings or processing-time result is claimed.

## Proposed outline

1. **Situation and problem:** “Before a purchase request can be reviewed, someone has to chase the missing details.” Show a fictional request missing its delivery date.
2. **Early outcome:** glimpse a complete request in a proposed review queue. The outcome is ready for review, not approved or ordered.
3. **Demo as proof:** label the rewind; follow one requester entering the delivery date, seeing the missing-field warning clear, checking the summary and submitting.
4. **Role handoff:** the coordinator opens that same request. Its information is present and the approval decision is visibly pending. The requester can see that status too.
5. **Payoff and next step:** the proposed workflow puts clarification before submission and keeps both people informed. Suggest testing one request type with sample data.

## Example story discussion

An initial “all purchasing features” angle would spread attention across supplier lists, budgets and reporting. The recommended angle follows one incomplete request to a reviewable submission. It gives the coordinator a clear operational benefit and the requester an understandable path, without inventing quantified savings.

Before production, ask the actual user whether incomplete requests are the problem to lead with and whether the complete-but-pending request is the right outcome. Record their real response and date in the project's brief. Do not copy an approval from this example.

## What is deliberately out of scope

Supplier onboarding, payment execution, budget enforcement, purchasing authority, AI assistance and automatic approvals. Add any of these only if the real user changes the pitch goals and provides evidence.

## Evidence and production direction

The [storyboard JSON](supplylane-storyboard.json) cites this fictional scenario as an assumption, not external proof. Its [rendered planning page](supplylane-storyboard.html) is a storyboard: no product interaction, audio or finished video.

Use a calm, conversational explanation. Let the missing-field correction and “pending review” state remain visible long enough to read. The requester should feel guided; the coordinator should see a complete request without being told that all purchasing problems are solved.
